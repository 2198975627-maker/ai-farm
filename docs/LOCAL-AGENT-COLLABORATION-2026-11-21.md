# AI Farm 本地多客户端协作实施报告

日期：2026-11-21。性质：可行性核实、实施计划与分阶段验收记录。

## 1. 目标与结论

目标不是让几个 API 模型扮演 Antigravity、Codex、Qoder、WorkBuddy、Hermes One，而是让这些真实客户端以自己的身份进入农场任务群，提出方案、领取分工、执行、交叉审查，向主人交付有证据的结果。

结论：统一群聊、授权分工和受控协作内核可行；五个客户端在当前 Windows 环境中全部实现无人干预、事件式双向唤醒，尚无充分证据。各客户端需要不同连接器，不能把“支持 MCP”“安装了程序”“任务已入队”当作实连完成。先建立可靠内核，再逐客户端验收，不用模拟回复填补缺口。

首阶段实现独立可测的协作内核和 Codex MCP 会话连接器；随后完成 HTTP、MCP 与传令兵统一鉴权及主人配对界面。内核与连接器尚未接成真实客户端授权执行服务，可信入口通过不等于桌面群聊或自动唤醒已经完成。

## 2. 不可突破的边界

- 仅主人与主人明确指定的主管可以发放执行授权；同事发言、提问、通知本身不能唤醒模型。
- 网页免费员工继续走传令兵，不加入本地 MCP 总线。
- 不新增定时轮询、到达速度公示或 @ 未读提醒；通过长连接、条件变量、客户端回调或明确的生命周期事件推进。
- 讨论、报告、审查必须来自真实参与者；没有可用模型就停下并说明原因。
- 只交换本任务必要的结论、证据、文件变更、测试结果和阻塞问题，不导入个人历史聊天。
- 不读取、复制或公开个人账号状态、私聊、密钥、私有仓库内容或本机绝对路径。
- API 密钥只通过环境提供。农场的短期连接凭据与模型密钥分开，不能出现在公开配置、URL、错误日志或任务正文中。
- 保持 Python 标准库和原生前端，零新增第三方运行依赖、零前端构建。
- 不自动批准客户端工具权限，不自动合并、推送、部署；保留各客户端的原生审批边界。
- 不承诺外部执行“恰好一次”：发送后结果未知时，不盲目重发、不换另一个模型重复执行。

## 3. 核实方式与当前证据

### 3.1 已做的检查

1. 只读检查农场消息、讨论、执行、MCP 与 HTTP 边界代码。
2. 读取公开的 HUD 原理说明及客户端文档，区分其源码能力、发行版能力和平台限制。
3. 仅检查目标程序的命令与安装元数据；没有读取用户聊天或账号凭据。

## 4. HUD 原理：借鉴什么，不照搬什么

### 4.1 可借鉴的机制

HUD 的中继只是入口，真正投递由客户端特定适配器完成。它并不是一个通用 MCP 调用就可以控制所有桌面软件。

- **真实身份定位**：发送者来自中继会话元数据、受控环境或客户端 Hook 的进程关联，而非任意 `sender_id` 参数。
- **优先使用会话所有者**：向持有目标线程的客户端发送，避免另起同一线程导致双重执行。
- **入队而不打断**：繁忙时等待空闲；入队、开始与完成分别记录。
- **发送前记账**：持久化请求标识与内容指纹；重复同一请求返回同一回执，修改内容后复用标识应拒绝。
- **不确定不重发**：字节可能已经发送时，超时、断线或崩溃保留 uncertain，而不是自动降级重做。
- **显式回传**：接收方用消息工具带 `reply_to` 回答；只在自己的窗口里说完，不代表群里收到。
- **有限讨论**：关联同一条链并限制往返，避免模型互相致谢或争论消耗额度。
- **审批留在客户端**：消息送达不等于批准文件写入和其他敏感操作。

### 4.2 当前 Windows 限制

HUD 的公开消息说明记载：

- Codex 通过桌面线程所有者或 App Server/共享队列操作；并非简单 `exec` 冒充控制现存会话。部分说明验证的是比本机更高的版本，必须重新做兼容测试。
- Antigravity 的 Windows 路线可以向现有会话发送，不能据此承诺新建或中断；它依赖本地语言服务的内部 RPC，不是 Google 的公开稳定自动化 API。
- WorkBuddy、Qoder 等 Hook 路线要等 `Stop` 等事件消费邮箱；公开说明明确 Windows Hook 安装/接收尚不支持。
- 已经完全空闲的 Hook 客户端，不一定会因邮箱多一条消息就醒来。
- Hermes 的监控支持不等于 Hermes One 原生聊天控制。

### 4.3 不照搬的部分

HUD 部分通路使用周期性检查、日志尾读、进程关联和内部协议。本项目不复制轮询方案，不扫描个人聊天来推断答案，不把内部接口当稳定公开契约，也不复制品牌图像或闭源服务。当前公开源码采用 Apache-2.0；本阶段仅参考原理，不复制实现，若后续复用代码必须单独核实对应版本许可并保留必要声明。

## 5. 首阶段检查发现的缺口

以下记录改造前的基线。HTTP 匿名入口、参数伪造身份及反射派发问题已在后续统一鉴权中收紧；真实客户端会话和执行服务的接线仍未完成。

- `office_store.py` 的群聊只追加记录，@ 不是唤醒动作。
- `bussend` 写入就标记 delivered；收件箱没有客户端确认和消费语义，因此“已投递”与“实际收到”混淆。
- 当前 MCP 中继 12 个工具主要转发到 Core；它本身不维持真实客户端会话，也不自动运行目标模型。
- 管理层讨论限制普通员工参与，不能直接作为五个执行客户端的任务群。
- `/api/action` 与 `/api/state` 仅有 Origin 检查，缺少可信身份认证；无 Origin 的调用可进入。
- 发送者、审查者等身份来自参数；反射式 `dispatch_action` 还会扩大外部可调用面。
- API/CLI 自动执行与桌面手工工单是分离通路，缺少统一运行凭证、在途去重与不确定结果状态。
- 自动编排的测试通过不等于这些本地应用已经接收、讨论并完成任务。

因此必须先收紧边界，再开放自动执行。只保护新增端点而保留旧的匿名执行入口不是有效修复。

## 6. 目标架构

```text
主人 / 明确指定的主管
    │ 创建任务群、预算、分工、执行授权
    ▼
农场可信入口 ── 身份绑定 / 任务范围 / 审批
    │
    ▼
协作内核 ── 消息顺序 / 显式回执 / 忙闲事件 / 有限轮次
    │                     │
    │                     └─ 持久执行账本：pending/running/unknown/terminal
    ▼
客户端连接器（能力各不相同）
    ├─ Codex：MCP 会话；后续研究原生 App Server 线程队列
    ├─ Qoder Desktop：主动 MCP + 经授权的本机桥接
    ├─ Antigravity：官方扩展优先，内部 RPC 单独实验
    ├─ WorkBuddy：本地助理入口 + 待确认的非轮询回执
    └─ Hermes One：待验证的认证网关事件流
    │
    ▼
结构化成果 → 独立审查 → 主管整合 → 主人最终验收
```

### 6.1 身份与权限

每个接入凭据绑定一个农场成员和当前会话，不能靠修改参数切换身份。主人配对、撤销和指定主管；主管只能在获准任务群中授权，不能配置凭据或把自己升为主人。网页成员无 MCP 身份。

凭据短期、可撤销，不存入 OfficeStore。重启后重新配对；执行账本保留，凭据不恢复。不同应用可能共享同一个 Windows 用户，本方案是应用协议边界，不是操作系统隔离，不能防御任意同用户恶意进程读取内存或用户文件。

### 6.2 消息不是执行授权

群消息包含 room_id、message_id、作者、类型、正文和必要的 reply_to。普通成员可在被邀请的群里讨论，但不能用提问、回复、冒充新链等方式启动其他模型。

执行授权单独包含 room_id、目标成员、工作说明、请求指纹、幂等键、批准者和状态。只有获准目标可以原子领取；一次只允许该成员有一个未决执行。接收群消息与领取执行授权分别确认。

### 6.3 事件驱动

进程内以 `threading.Condition` 等待明确事件，阻塞读取客户端 stdio 或接收客户端回调。超时是单次等待的截止条件，不由定时器循环请求收件箱。网络订阅、取消及客户端会话所有者尚需在后续阶段联调，不能把等待工具描述成能唤醒已退出的客户端。

### 6.4 持久化与结果未知

先持久化领取记录，再向外部客户端发送。结果未知时阻塞该成员的重复执行，必须由可信证据或主人处理后解除；重启时原 running 记录转 unknown，不能重新排队自动执行。关闭、取消和撤销不能保证已经发出的外部任务已停止。

## 7. 协同质量设计

### 7.1 一次任务的工作协议

1. 主人说明问题、输出物、约束、可写工作区与验收标准。
2. 主管选择必要参与者，而不是每个任务都叫醒五个客户端。
3. 对存在实质分歧的任务，收集独立短方案，进行有限次数的证据对照；简单任务直接派单。
4. 分工写明负责人、依赖、输入、输出、完成条件及不能触碰的文件。
5. 工作区写入范围不重叠；需要同时修改同一文件时串行，或经主人同意采用独立 worktree 后审查合并。
6. 执行者交回结论、变更文件、测试命令/真实结果、未解决问题及必要证据。
7. 独立审查者检查成果，不允许执行者给自己盖章；有问题才触发有次数上限的修订。
8. 主管保留异议、解释取舍、整合结果，主人最终验收。

### 7.2 防止“热闹但没有产出”

- 群聊围绕同一任务与交付物，默认不自动广播全部历史。
- 提问必须指出阻塞点；回复应完成一次必要交接，不自动发送礼貌性往返。
- 轮次、调用数、耗时、文本体积均设服务端上限。初始建议为每群最多两轮方案对照、最多八次模型执行授权；这些是拟议限制，不是实测性能或节省金额。
- 计数基于农场运行标识，不能由客户端改 chain_id 清零。
- 不确定的价格、额度、用量留空或标未知，不用零冒充已测量。
- 不按发言数量衡量质量；以验收项通过、证据完整、重复执行数和人工介入原因衡量。

### 7.3 质量指标的测量方法

| 指标 | 证据 | 当前状态 |
| --- | --- | --- |
| 实际收件与结果回传 | 对应客户端会话标识、执行标识、显式确认和成果 | 尚未真实多客户端验收 |
| 重复执行防护 | 同幂等键并发提交、重启恢复、超时场景 | 由确定性自动测试验证，不能代替外部恰好一次保证 |
| 授权正确性 | 普通成员、伪造主管、撤销后请求均被拒绝 | 内核和统一入口隔离测试通过；真实客户端执行授权仍待接线 |
| 协作成果质量 | 独立审查记录和主人给定验收项 | 尚未测量 |
| 成本 | 客户端真实 usage/账单字段；无法取得就未知 | 不估造节省比例 |
| 人工介入 | 登录、审批、客户端关闭、协议不支持、结果未知分别记录 | 后续真实验收采集 |

## 8. 实施阶段与放行门禁

### P0：核实与方案（已完成）

完成五客户端身份/入口检查、HUD 原理核实、Codex 无模型握手及原有 41 项回归基线。没有个人配置修改，没有实际模型调用。

### P1：可独立验收的内核与连接器（已完成隔离验收）

- 增加协作内核：运行期身份绑定、任务群、消息回执、受控执行授权、事件等待、幂等、重启未知状态、独立审查和关闭门禁。
- 增加 Codex MCP 长连接客户端：默认只读、保留审批、不使用 shell 拼接、按 threadId 继续、超时不重发、无全量聊天落盘。
- 收紧 Core 反射式动作派发，拒绝非公开动作；这不是完整身份认证。
- 编写隔离测试，确认没有新依赖、没有在旧匿名接口暴露新能力。
- 不在这个阶段修改五个客户端的权限或连接器配置。

### P2：统一可信入口和可操作界面（鉴权已完成，执行接线待完成）

- 已对现有 HTTP 读写接口统一鉴权：loopback 绑定、精确 Host/Origin、CSRF、短期会话、撤销和限界请求。
- 已实现一次性本机主人配对、HttpOnly/SameSite Cookie，以及按成员与工单绑定的专属凭据；不共用主人凭据。
- MCP 生产入口已转为可信共享 HTTP 后端，发送身份来自连接绑定；拒绝匿名启动、代理和重定向，不再直接打开个人状态文件。异步事件等待、取消与断线执行对账仍待接线。
- 传令兵已改为单工单、单标签页及站点绑定；拒绝未绑定取最新任务、匿名直连回退和网页合成点击。发送前持久化占位，未知结果不自动重发。
- 已提供配对、发放与撤销界面；真实任务群 connected/waiting/acknowledged/running/unknown 界面仍待连接内核，不能按图标推断在线。
- 鉴权通过不是自动唤醒放行；须继续完成执行接线与真实客户端验收。

### P3：真实双客户端闭环

优先验证 Qoder 主动会话与 Codex 受控会话。使用新建的隔离任务，不附着或读取个人历史会话。

流程：主人授权 → Qoder 提出短方案 → Codex 回应并执行隔离小任务 → Qoder 独立审查 → 修订（必要时）→ 农场汇总。分别记录实际会话、任务授权、回执、文件与测试证据。Qoder 主动接入成功不等于已支持空闲桌面自动唤醒，后者单独验收。

需要主人确认：连接器/插件安装或设置变更、配对身份与主管、任务工作区、实际模型调用及预算。正常工具权限仍由原客户端处理，不因本报告自动扩大。

### P4：补齐其余客户端

- Hermes One：先验证合法认证网关的会话建立、同会话续接、完成事件和与桌面会话的所有权冲突；标准库 WebSocket 实现成本与稳定性需评估，不偷偷增加依赖。
- Antigravity：先验官方 CLI/Hook 可用性；若确需 HUD 式内部接口，由主人明确同意实验范围，固定兼容版本，不扫描令牌、不绕过权限。
- WorkBuddy：先解决官方授权与非轮询回传路径；未解决前明确显示受限，不接云任务冒充本机。
- 任一客户端更新后，以小型协议自检与真实隔离任务重新验收，不因旧版本成功永久标为可用。

### P5：协作质量与恢复验收

统一鉴权的新增交付：

| `browser-extension/background.js`、`content.js` | 单标签页/单站点/单工单绑定；无匿名取最新任务或直连回退；拒绝网页脚本合成点击；发送前持久化占位 |

圆桌协议：

1. `createbigtask` 默认 `standard`；只有显式 `roundtable` 才开启。A/B/C 必须为三个不同厂商、三个不同模型的 2F 经理；免费网页和 1F 员工不得入席。付费网页/订阅及桌面席位人工交接，不冒充 API 自动调用。
2. Stage 0 只收各子单的结论、改动文件和测试结果，不导入聊天历史；代码子单还须独立非干跑审查通过。模拟标记不能经 HTTP/MCP 旧包装入口变成真实资料。
3. Stage 1 A 给 B 精确提示词、约束、验收；Stage 2 B 产出 Draft v1；Stage 3 C 直接给 P0/P1 问题与 Refined v2，代码任务另带实际 `git diff --stat`。
4. Stage 4 分别调用 A、B 对比，每人至多三条短评并建议 B/C；不把另一人的意见继续转发，`reply_hint=false`。固定一轮对抗和一轮比较，最多五次自动经理调用，不能清零续轮。
5. A/B 比较结束仅到 `awaiting_owner`；主人明确选 B、C 或退回重修。选择保留对应原文和另一份稿件；重修终止本轮，不自动再烧额度。
6. 子单和经理请求均有 SHA256 回执。模型调用前先持久化预留，运行中/完成/未知不得盲目重发或自动回退。验证码等卡点只允许主人确认原任务不在运行后，单张跨厂商转交。
7. 回执预留、资料回收、独立审查、单点转交和人工定稿落盘失败时回滚；外部调用之后失败保留未知状态。错误账本不保存原始异常中可能含有的密钥或本机路径。

自动化的实际边界：API/CLI 可在主人确认后推进当前经理阶段；UI 当前一次推进一步，人工席位停在复制提示词/回填，最后必停在主人定稿。没有无限群聊、后台定时轮询或自动唤醒未接通的桌面软件。子单依赖批处理与模型编排只能在明确支持的执行通道内使用。

浏览器验收使用隔离临时状态，适配器被测试替身禁止真实调用。已验证配对、错误码/CSRF、凭据发放撤销、关闭清理、默认普通模式、缺席/缺资料拒绝、旧验收入口拒绝、干跑只读、子单汇报、五次人工回填、B/C 保留及主人采纳 C。无效 JSON 保留输入，不推进阶段。原生隐藏浏览器无法截图或可靠验键；另导出无凭据的夹具 DOM，在 headless Chromium 以 1440×900、390×844 检查进度和成果对比布局。关闭按钮和合成 cancel 事件通过；物理键盘 Escape、真实设备及真实厂商网页未验收。
